# 赛事需求信号协作

赛事主办方与城市经营主体交换分级需求信号,保留预测版本和实际回看依据。

`fixtures/demand_signal.json` 保存一条经过脱敏的业务样例,源代码只定义读取这份样例所需的最小合同。后续模块应保持既有标识和时间含义,新增状态必须说明迁移方式。

## 模块结构(`src/event_signal/`)

- `contracts` — 既有最小合同(`DomainRecord` / `load_record`),保持不变。
- `timeutil` — 带时区的 ISO 8601 时刻与半开时间窗;跨午夜场次按绝对时刻比较,营业日归属窗口开始时刻的本地日期。
- `models` — 不可变领域模型:信号版本、供给登记、实绩记录、授权事件。
- `dedup` — 同源去重:内容指纹幂等 + revision 单调递增;同源重叠告警。
- `store` — 只追加事件存储,所有查询支持 as-of 历史重建。
- `access` — 可见级别(public / network / restricted / private)与授权事件的 as-of 求值。
- `analytics` — 需求聚合、实绩聚合(k 匿名抑制)、逐版本误差回看。
- `audit` — 增配重建与损失归因(仅运营中心)。
- `service` — `DemandSignalService` 门面:发布/修订/撤回、供给登记、实绩回填、授权与全部查询。

## 版本与状态治理(迁移方式)

- **标识**:`(source, record_id)` 是业务身份,`revision` 单调递增且必须连续;`occurred_at` 是业务时间,`recorded_at` 是系统追加时间,迟到数据由此区分 —— 迟到或修正数据以更大的 revision 形成新版本,从不改写历史。
- **撤回**:`status = withdrawn` 的新版本(墓碑),不是删除;as-of 撤回时刻之前仍重建出 active 状态。
- **同源重试**:相同 `(source, record_id, revision)` 且内容指纹一致 → 幂等返回既有版本;同 revision 不同内容 → 拒绝,必须提升 revision。
- **供给登记**:永久绑定登记时所见的 `(signal_id, signal_revision)`;登记时该版本必须已发布且对登记方可见,信号已撤回(以决定时刻为准)则拒绝。
- **权限变化**:授权/收回是追加式事件,按 `effective_at` 参与 as-of 求值;可见级别本身的变更通过新 revision 生效,历史版本仍按当时的级别判定。
- **新增枚举取值**(用途、可见级别、状态等)为增量变更:旧版本读取端会拒绝未知取值,需先升级读取端再放开生产端;不兼容变更须提升 `schema_version` 并另出迁移说明。历史版本不可变,因此任何新增状态都不需要数据迁移。

## 隐私与聚合协议

- 单个订单明细不进入系统;实绩只以 (参与方, 指标, 地域, 时间窗) 的聚合形式上送。
- 非运营中心视角下,贡献方少于 k(默认 3)的实绩聚合被抑制(`suppressed`),误差回看对发布方同样适用该抑制。
- 需求聚合按查看者的可见级别过滤;上级地域信号只作背景、不计入合计;同源同地域同指标的时间窗重叠以告警提示可能的重复计入,不擅自合并。
- 误差与损失归因仅发布方(自身信号)与运营中心可见;增配重建与损失归因仅运营中心可查。
- 跨窗口口径不一致时按时间比例分摊并标记 `prorated`;损失归因只使用登记方自身的实绩,不触碰他方明细。
